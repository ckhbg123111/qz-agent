# 宣教智能体推送提测报告

## 一、提测背景

本次需求为宣教智能体新增基于院内事件的规则化推送能力。系统接收病历确诊事件、处方开具事件后，根据配置化规则判断是否命中对应病种及推送标签，并触发即时推送或创建延时推送任务。

推送规则与 tag 编码通过表配置维护，后续新增或调整病种规则时，优先通过配置数据完成，减少重复编码。

## 二、提测范围

本次提测覆盖开发文档中规则 `0~10`，其中规则 `6` 明确暂不开发，不纳入本次测试范围。

本次纳入提测的接口：

- 病历确诊接口：`/api/b2b/qz/hp/diagnosis-event`
- 处方开具接口：`/api/b2b/qz/hp/prescription`
- 延时推送定时任务
- 推送规则配置读取与匹配逻辑
- 推送成功记录幂等控制逻辑

本次不纳入提测的内容：

- 检验单开具接口：`/api/b2b/qz/hp/lab-order-event`
- 糖尿病检验单触发规则，即规则 `6`
- 肾穿刺手术相关规则，即规则 `11~14`
- 屈光手术相关规则，即规则 `15~17`

## 三、提测功能清单

### 1. 病历确诊事件即时推送

病历确诊接口收到 `diagnosisCodeSystem == "ICD-10"` 的请求后，按诊断码子串匹配对应规则，命中后触发即时推送。

需验证的即时 tag：

- 胃炎：诊断码包含 `K29`，触发 `WY_QZ`
- 消化性溃疡：诊断码包含 `K25`、`K26` 或 `K27`，触发 `XHKY_QZ`
- 炎症性肠病：诊断码包含 `K50` 或 `K51`，触发 `YZCB_QZ`
- 糖尿病：诊断码包含 `E10`、`E11` 或 `E14`，触发 `TNB_ZBQD`

### 2. 病历确诊事件延时推送

病历确诊即时规则判定为可推送后，系统需要基于本系统记录的可推送时间创建对应延时任务，不依赖微信实际推送是否成功。

需验证的延时 tag：

- `WY_FCTX`：胃炎确诊可推送时间后 `14` 天
- `XHKY_FCTX`：消化性溃疡确诊可推送时间后 `1` 个月
- `YZCB_FCTX`：炎症性肠病确诊可推送时间后 `1` 个月
- `TNB_ZN`：糖尿病确诊可推送时间后 `4` 小时

### 3. 处方开具事件即时推送

处方开具接口收到 `diagnosisCodeSystem == "ICD-10"` 的请求后，需同时满足糖尿病诊断码与药品名称匹配条件，才触发处方宣教推送。

命中条件：

- 诊断码包含 `E10`、`E11` 或 `E14`
- `medicineItem` 中任一 `medicineName` 包含以下关键词之一：
  - 胰岛素
  - 利拉鲁肽
  - 司美格鲁肽
  - 替尔泊肽

命中后触发 tag：`TNB_CF`。

### 4. 处方开具事件延时推送

处方即时规则判定为可推送后，需要创建随访类延时任务。

需验证的延时 tag：

- `TNB_SF`：糖尿病处方可推送时间后 `14` 天

### 5. 规则配置能力

需验证新增宣教推送 tag 不再硬编码在新增业务逻辑中，而是通过配置表维护规则和 tag 映射。

重点验证：

- 即时规则可从配置中读取并完成匹配
- 延时规则可从配置中读取并完成任务创建
- 规则启停、规则条件、tag 映射与开发文档一致
- 已有 `PushTaskConstants` 逻辑不受影响

### 6. 幂等与去重能力

同一患者、同一 tag 在本系统中只允许成功推送一次。幂等维度为 `patientId + tag`，不区分就诊号。

重点验证：

- 同一 `patientId + tag` 已成功推送后，再次触发不应重复推送
- 同一患者不同 tag 可分别推送
- 不同患者相同 tag 可分别推送
- 同一患者同一 tag 的失败记录不阻止后续重试或再次触发
- 延时任务创建和执行阶段都需要遵守成功记录幂等规则

## 四、重点测试场景

### 1. 正向命中场景

- 胃炎确诊：`diagnosisCode = "K29"` 或包含 `K29` 的扩展码，触发 `WY_QZ`，并创建 `WY_FCTX`
- 消化性溃疡确诊：分别使用 `K25`、`K26`、`K27`，触发 `XHKY_QZ`，并创建 `XHKY_FCTX`
- 炎症性肠病确诊：分别使用 `K50`、`K51`，触发 `YZCB_QZ`，并创建 `YZCB_FCTX`
- 糖尿病确诊：分别使用 `E10`、`E11`、`E14`，触发 `TNB_ZBQD`，并创建 `TNB_ZN`
- 糖尿病处方：诊断码命中糖尿病，药品名称包含胰岛素、利拉鲁肽、司美格鲁肽或替尔泊肽，触发 `TNB_CF`，并创建 `TNB_SF`

### 2. 反向不命中场景

- `diagnosisCodeSystem != "ICD-10"` 时，接口返回成功，日志记录跳过原因，不触发推送
- `diagnosisCodeSystem` 为空时跳过，不触发推送
- `diagnosisCode` 为空时跳过，不触发推送
- `patientId` 为空时按接口必填校验处理
- 诊断码不包含配置子串时不触发推送
- 糖尿病处方中药品名称不包含指定关键词时不触发 `TNB_CF`
- `medicineItem` 为空时不触发 `TNB_CF`
- `medicineItem.medicineName` 为空时不触发 `TNB_CF`
- 处方接口允许 `prescriptionDate` 为空，不应因此影响规则判断

### 3. 延时任务场景

- 即时规则命中后，立即创建对应延时任务
- 延时任务的基准时间为本系统记录的规则可推送时间
- `plusHours(4)`、`plusDays(14)`、`plusMonths(1)` 的触发时间计算正确
- 延时任务执行前如发现 `patientId + tag` 已成功推送，则不再执行推送
- 延时任务已存在或已成功推送时，不应重复创建同一患者同一 tag 的有效任务

### 4. 时区场景

本次规则 `0~10` 中没有固定晚上七点、晚上八点等时刻，但延时任务仍需确认系统统一使用 `Asia/Shanghai` 时区计算和调度，避免跨天、跨月场景出现偏差。

### 5. 配置数据场景

- 配置表中规则 tag 与需求文档一致
- 配置表中诊断码关键词与需求文档一致
- 配置表中药品名称关键词与需求文档一致
- 配置表中延时规则与前置规则关系正确
- 配置缺失、禁用或异常时，系统应记录日志，且不影响接口成功返回策略

## 六、回归测试建议

建议回归以下已有能力：

- 原有 `PushTaskConstants` 相关推送逻辑不受影响
- 推送接口调用链路保持兼容
- 推送成功、失败记录状态流转正常
- 定时任务扫描与执行逻辑正常
- 业务接口在规则未命中、数据为空、非 ICD-10 等场景下仍可稳定返回
- 日志中可追踪规则命中、跳过、创建延时任务、幂等拦截等关键节点

## 七、风险点

- 规则配置数据错误会直接影响推送准确性，需要重点核对初始化数据。
- 诊断码和药品名称均为子串匹配，需要关注误命中和大小写、空格、特殊符号等边界输入。
- `patientId + tag` 为全局成功幂等维度，不区分就诊号，测试时需避免复用已成功推送过的患者数据导致误判。
- 延时任务基准时间为本系统判定可推送时间，而不是微信实际推送完成时间，需要测试侧按该口径验收。
- 失败记录不阻止后续重试，需区分成功幂等和失败可重试两类行为。
- 月份延时使用 `plusMonths(1)`，月底日期可能存在自然月进位差异，需要覆盖月末边界。

## 八、提测结论

本次宣教智能体推送需求已按开发文档范围提测，测试重点为病历确诊事件、处方开具事件、即时推送、延时任务、配置化规则与 `patientId + tag` 幂等控制。

请测试侧优先覆盖规则 `0~10` 中除规则 `6` 外的全部场景，并重点验证非 ICD-10 跳过、空字段跳过、延时任务创建与重复推送拦截逻辑。
